# PM 运行规则与 QA 门禁

这个文件记录用户对 PM / 开发 / 测试协作方式的长期要求。它不是需求池，不分配 AR 编号，也不进入业务发布候选。

## 文档边界

- `docs/backlog.md`：只记录产品需求、生产问题、发布准备、hotfix、基础设施缺口。
- `docs/release_board.md`：只记录可发布事项、发布 lane、QA lane、hotfix lane 和 release checklist。
- `docs/pm_operating_rules.md`：记录 PM 工作规则、测试门禁、线程协作要求、用户输出格式。
- `docs/pm_dispatch_queue.md`：记录已准备派发但因目标线程 busy 而暂存的任务。
- `docs/thread_handoff_log.md`：记录真实派发、回传、测试结论和发布门禁证据。

## PM 统筹规则

- 用户只和 PM / 发布控制线程说需求、生产问题、发布判断或普通咨询。
- PM 先判断类型：新需求 / 生产问题 / 发布决策 / 普通咨询。
- 内容质量、用户可见输出、发布门禁或高歧义需求，PM 必须先和用户对齐方案，再派发。
- 用户说“可以 / 方向认可 / 先做这个”只代表方向同意，不等于需求已确认。对新需求、范围不清的生产优化、会影响流程/状态/字段/卡片/通知的需求，PM 必须先输出轻量方案，说明目标、范围、用户可见结果、关键规则、测试口径和发布路径；只有用户明确确认方案后，才允许派发开发任务。
- PM 向用户做最终确认时，不能只给方向或一句话取舍；必须给“方向 + 可执行详细方案 + 明确决策点”。方案至少覆盖：做什么、不做什么、用户最终会看到什么、核心规则、异常/边界、测试方式、发布路径和需要授权的事项。
- 遇到复杂需求、高歧义需求、跨链路需求、内容质量/用户体感类需求、反复返修后仍未达标的需求，PM 应先开评审再派开发。评审可以只由开发线程做，也可以在 PM 判断必要时拉测试线程参与对抗性评审。评审不是实现任务，必须先梳理目标、真实链路、职责边界、字段/状态契约、测试口径和风险，再汇总成 PM 可决策方案给用户确认。
- PM 可以在评审中给出自己的判断和推荐方案，但最终必须把开发评审、测试评审和 PM 判断合并成一份面向用户的决策摘要。未经用户确认，不得把评审结论直接当作开发授权。
- PM 需要用户拍板、授权、确认方案、确认发布或人工验收时，输出必须以 `【需要你决策】` 开头。
- PM 只是同步阶段结果、派发状态、测试结论或无需用户回应的信息时，输出必须以 `【结论】` 开头。
- PM 管理文档默认作为本地运行台，不提交、不 push，除非用户明确要求。
- PM / 发布控制线程不承担生产发布执行职责。PM 负责发布方案、分工、授权确认、任务派发、进度监督、证据核验、风险收口和用户汇报；生产发布执行必须派发给生产分支线程或明确的执行线程完成。
- 用户同意发布方向，不等于授权 PM 线程亲自执行生产 `git push`、`git merge`、`git pull`、runtime sync、生产 Skill 同步、SCF 部署、生产表 schema/backfill、真实通知或 production smoke。PM 必须先给出逐步发布执行清单和影响边界，再派发生产线程执行。
- 发布授权必须拆成两层：用户同意发布方向后，PM 仍必须给出具体执行步骤、影响系统、停止条件和回滚/恢复方式；只有用户确认或项目既定发布任务卡明确后，生产线程才执行对应步骤。
- PM 可以直接维护 PM 管理文档、整理状态、写任务卡、核验证据和输出验收结论；PM 不直接执行会改变仓库、分支、worktree、runtime、云端、飞书表、通知、ledger 或历史证据的动作。
- PM 可以直接做生产只读诊断，但一旦下一步需要改代码、创建或修改 worktree、运行产品测试、commit/push、发布、runtime/LaunchAgent 变更或外部写入，必须先派发到对应固定开发、测试或生产线程；问题再小也不例外。
- 用户说“确认”默认表示确认方案或确认 PM 可以派发，不表示授权 PM 当前线程亲自执行。若用户确实要 PM 当前线程执行某个状态变更动作，必须明确说“允许当前 PM 线程执行”，且 PM 仍要先说明影响边界。
- 本地 release 分支清理、`git worktree remove`、`git branch -d/-D`、删除本地发布目录、删除远端分支、清理发布 artifact 或 ledger，即使不写生产业务表，也属于执行动作；应派给生产/执行线程，不能由 PM 线程顺手操作。
- 如果 PM 线程误执行了执行动作，必须立即停止，不继续做后续清理或发布；先记录已发生动作、未发生动作、影响边界、恢复可能性和防复发规则，再由用户或执行线程决定下一步。

## 固定线程协作

- 固定线程负责长期交付；子 Agent 只用于临时并行脑力。
- PM 是唯一派发者；开发、测试、生产线程之间不得互相下达新任务。
- PM 使用线程派发工具时默认必须省略 `model` 和 `thinking` / `reasoning effort` 参数，保留目标线程当前由用户选择的模型与推理设置。只有用户在当前任务中明确指定目标模型或推理强度时，才允许覆盖；不得因任务复杂、发布风险或 PM 自己的判断擅自切换模型。
- 用户选择 projectless / “不在项目中工作”时，线程和 automation 必须保持 projectless；不得为了获得 cwd 而擅自重新绑定项目。若 official control 不能同时表达 projectless 与所需生产目录，应明确报告产品限制，并仅使用用户确认的 UI 修改或显式生产入口；不得 raw-edit App 隐藏配置。
- PM 派发前必须读取目标线程状态。
- 目标线程 idle 时才发送任务卡。
- 目标线程 active 时，不发送消息，改写入 `docs/pm_dispatch_queue.md`。
- 执行线程完成后只回传 PM，不能直接指挥其他执行线程。
- PM 收到回传后先核验证据，再决定下一步派发、排队或向用户汇报。

## 开发-测试闭环

### 门禁强度与返工收敛

- 门禁必须先区分 `system/run`、`source/account`、`candidate/item` 和 `quality` 四个层级。不得因为实现方便，把低层级失败自动提升为整条生产链 hard stop。
- 只有日期/run/source identity 错误、stale/cross-run substitution、secret/auth 泄漏或失效、外部写入/read-back 不一致、system receipt/signature/DB/plan drift、不可恢复状态污染等系统级风险，才默认整批停止并零下游输出。
- 单来源、单账号、单候选、单篇读取失败必须局部隔离：失败项零 artifact，不得 fallback 或补位；同批其它身份和证据完整的成功项继续，整体明确标记 `partial` / `completed_with_failures` / non-green，不能冒充 full success。
- 内容长度、表达风格、质量分、样例偏好等质量信号默认不是数据真实性证明。除非用户明确把某项质量阈值定义为业务硬门，否则只能作为质量标注、排序信号或候选级拒绝理由，不能据此丢弃整批真实数据。
- 在用户已授权的同一目标和影响边界内，可逆、只读、无外部写入的诊断与 read-back 默认自动推进，不应对每个 retry、GET-only 或本地证据检查重复索要授权。涉及 secret、账号所有者交互、不可逆动作、真实写入、通知或新增成本边界时仍须停线确认。
- 新门禁设计前先观察真实 payload、失败 telemetry 和真实运行环境，再构造等价 fixture；不得只根据理想 mock 推导生产合同。缺少定位信息时先补 observability，不先叠加新的身份层、签名层或授权层。
- 每个 hard gate 必须能指出已确认的业务需求、真实失败和用户可见损害。内部 provenance 更完整、证据更漂亮或架构更严谨本身不是业务需求；现有 canonical record、稳定业务键和 exact read-back 足以证明外部结果时，不得继续新增 fingerprint、identity、signature、attestation、manifest 或授权层。
- 同一根因只形成一个收敛修复包、一个 production-base 窄 RC 和一次独立 QA。QA 的多个发现应一次性汇总返修，不得把每个字段、边缘输入或报告差异拆成独立 micro-RC / micro-recheck。若根因或产品目标实质变化，PM 先重新校准方案再决定是否开启新一轮。
- 用户明确接受残余风险、把事故降级为 non-blocking、要求恢复正常运行或要求“不再修改直接发布”后，PM 必须记录残余风险并停止扩张安全工程；只有出现新的真实业务影响证据或用户主动要求 hardening 时才能重开。
- 业务完成与 hardening 完成必须分开。只影响 observability、诊断完整性或 defense-in-depth 的问题进入 backlog，不得继续阻断已完成的业务链路；仅当它仍可能造成错批次、stale 替换、重复/错误外部写入、secret 泄漏或不可逆污染时才保持 hard stop。

- 开发线程完成后主动回传 PM；PM 自验后再派测试线程。
- 测试线程默认不改功能代码，只做独立验证、对抗性审查、staging/test 验证和证据整理。
- 测试发现 bug 时回传 PM，不直接打断开发线程。
- PM 合并测试结论和自己的验收结论后，再决定是否派发返修。
- 测试线程回传 `QA Passed`、`Flow QA Passed` 或 `Waiting PM Review` 后，PM 必须单独做 PM 验收，不能只登记测试结论。PM 验收至少检查：测试是否覆盖用户真实目标、是否在正确运行环境或等价测试环境验证、是否存在被说过头的结论、生产边界是否安全、剩余风险是否足以进入 release candidate。
- PM 验收必须回到用户最初提出的原始需求和用户可见结果，而不是只检查上一轮 PM 派发给开发/测试的返修项是否完成。若返修项通过但还不能证明原始需求达成，应标为 `QA Passed / Waiting User Review`、`L3 Passed / Waiting User Editorial Review` 或等价状态，不能标 `PM Accepted`。
- PM 验收通过后，状态应从 `Waiting PM Review` 推进到 `PM Accepted / Ready for RC Regression` 或等价状态；如果 PM 发现测试覆盖不足，应明确降级为 `Needs Flow QA`、`Needs User-visible QA`、`Needs Rework` 或其它可行动状态。
- PM 向用户汇报验收通过时，必须同时带上测试结果和实际效果证据，不能只说“我验收通过”。至少应包含：测试线程结论、关键测试命令/环境、真实样例或输出路径、用户可见结果、未覆盖项和剩余风险。内容/选题类需求还必须给出可读样例或样例路径，方便用户判断实际体感。
- 对内容/选题/文案/卡片体验类需求，PM 在标记 `PM Accepted` 前必须把测试文件或可读样例交给用户：至少包括候选 CSV/JSON、最终用户可见卡片或文档、截图/DOM 证据、代表性样例标题和字段片段，以及这些样例如何回应用户原始问题。用户没有看到实际样例前，最多只能标 `Waiting User Review`。
- 内容质量需求不能以黑盒结论收口。PM 必须能解释真实运行链路、字段 owner、Skill / 代码 / fallback / validator 各自职责，以及用户可见结果如何从源内容生成。用户质疑“为什么这样选/为什么这样写标题”时，先做机制解释和必要评审。
- 如果内容输出出现同构、模板化、固定角度或“代码替 Skill 思考”的迹象，不得继续堆小补丁或只修样例；应先评审 Skill prompt、runner hint、deterministic fallback、field contract 和测试口径，确认哪些预设应降级为事实材料，哪些才是质量判断。
- 用户提供的案例库默认是人格、判断习惯和表达风格参考，不是选题事实来源、内容证据库或每条候选必须引用的“案例锚点”。除非用户明确要求案例复用，系统不得把案例库内容包装成来源证据、要求逐条 case mapping，或在用户可见选题里暗示案例事实参与论证。
- 人格/风格参考必须真实进入主编判断运行时，而不能只在报告、文件路径或仓库镜像中存在。内容类架构变更的自验包必须记录实际 Skill 文本路径/hash、实际嵌入的人设/风格参考路径/hash，以及该参考是 embedded、retrieved 还是 reference-only；repo mirror 与 production/global private Skill 的差异必须显式暴露。
- 当用户要求“像我一样思考”时，主编阶段先输出自然的选择判断、来源标题钩子、拒绝的俗套角度、Austin 切入和标题方向；实验、验证、资产和表字段只能在后续映射阶段生成，且不得反向改写主编已确定的标题/命题。deterministic code 只提供来源事实、去重和安全 guard，不得预设标题、母场景或主编角度。
- 这类架构的 QA 前必须有可执行结构证明：第一阶段输入不含旧可见字段/实验卡措辞；第二阶段不得发明第一阶段不存在的角度；真实运行时 Skill 与测试 Skill 的 provenance 可核验；至少用用户指定反例证明工作字段语言不会泄漏到前台标题。单靠禁词、报告展示、field guard 或单样例改写均不得作为通过依据。
- dev/test 自动返修最多 3 轮，指“测试不通过 -> 开发修复 -> 测试复测”的循环。
- 用户与 PM 之间的人工需求澄清、方案确认、用户验收反馈，不计入 dev/test 返修轮次。
- 用户反馈只有在明确改变了产品目标、验收口径或架构方案，并由 PM 重新汇总确认后，才能开始新的 0/3 迭代；标题微调、样例意见、技术门禁拆分、artifact 修复、runtime blocked 都不能自动重置计数。
- 当用户明确确认一次实质性重构并明确要求重设 QA 轮次时，PM 必须把旧架构 QA 归档，新的实现从 `0/3` 重新计数。重设只适用于新架构合同，不能用来继续旧实现的小修循环。
- QA 返回 `Failed`、`Blocked`、`Partial`、`Artifact Inconsistent` 或“技术通过但内容门未过”都占一次 QA 槽。不得把同一已确认方案拆成“技术 QA”“内容 QA”“展示 QA”来绕过三轮上限。
- 同一方案达到第 3 次 QA 返回后，PM 必须停止自动“QA fail -> 开发小修 -> QA”循环，先向用户报告准确轮次、失败模式和可选路径；只有用户明确决定继续投入、降级目标、拆新需求或接受风险后，PM 才能派下一步。

### 开发自验门（QA 前置）

- 每次 QA 打回后，开发线程必须先完成与 QA 失败项一一对应的开发自验，PM 审核自验包后才允许占用下一次 QA。
- 内容/Skill/标题类开发自验包必须包含：失败样例的 before/after、fresh real Skill 输出路径（不得只用 aggregate-only/旧 rows）、质量门计数、batch/guard 最终态、相关单测和回归、未覆盖风险。
- 开发自验若仍有 quality gate fail、fresh replay 未完成、失败样例未覆盖、batch note 与最终 rows 不一致或只证明代码路径未证明实际输出，开发不得交 QA；应留在开发线程继续定位。
- QA 只验证“开发已自证修复后是否仍有遗漏、回归或用户体感问题”，不是替开发逐轮试错的运行环境。
- 对实验、验证方式、标题思路等工作字段的质量审计，应与用户可见标题/命题的 hard gate 分开；不得因正常工作语言误杀自然前台标题，也不得借此放松真正的前台任务壳检查。

### 内容主编链路零 fallback 门禁

- 当用户明确要求零 fallback 时，active development/test/production path 不得保留可配置的 deterministic、legacy、old-Skill、old-persona、summary-substitution 或 report-only fallback。失败必须 fail closed，并产生可读错误、阶段状态和恢复入口。
- exact source 无法打开、研究不完整、Skill 输出不合约、证据 hash 不匹配或映射发生漂移时，该候选必须停止，不能用标题/短摘录、搜索摘要、旧 hook、默认角度、旧 Skill 或模板字段继续生成标题、推荐或卡片。
- 用户可见来源身份字段也必须零 fallback：`原始来源标题`、`原始发布文案`、`来源摘要`、`受众钩子` 是不同语义，缺失时只能留空或显示明确缺失提示，禁止用 `来源内容`、标题、摘要或其它字段交叉回填成看似完整的原始来源信息。可见闭环校验必须从主编最终原始行开始，不能只从 writer 加工后的 expected rows 开始。
- exact-source 证据只有在 raw DOM/body 文件真实存在、文件 SHA256 与声明一致、关键 literal excerpt 可在标准化 raw capture 中定位时才可进入 research；结构化字段、截图、任意 64 位 hash 或不存在的路径不能替代 raw source artifact。该门必须覆盖所有 adapter，包括 Douyin。
- 零 fallback 静态审计必须覆盖主链、writer/card 和所有 PM/QA 用户可读产物，包括 sample report、progress、title/body check、trace 与 self-acceptance 文档；不得只扫描 engine 关键词。若 `原始来源标题` 为空，任何报告也不得从 `来源内容/原始发布文案/来源标题` 回填并继续标成“原始标题”。
- 零 fallback 审计范围必须列全用户语义 owner，不得只维护一个不完整字段白名单。除来源身份外，`Austin改写理由/标题思路`、`选题命题/选题标题`、`我的切入/locked angle`、研究摘要、受众钩子和主编摘要也不得相互代填。可见闭环 validator 必须让 owning field 缺失直接失败，不能在 expected snapshot 阶段用旧别名、锁字段或其他用户字段补齐后再宣称同态通过。
- 零 fallback 证明不能只识别 `a or b`、三元表达式等语法外形；必须覆盖赋值传播、变量别名、顺序 `if`、early return、嵌套分支和默认参数等跨语句数据流。同时必须对每个 active semantic transformation 跑行为矩阵：将 owning field 置空、同组其他字段填唯一 sentinel，输出只能保持空/显式失败/显示占位，不能出现其他字段 sentinel。静态审计与行为矩阵任一失败，均不得进入 QA 内容或可见流。
- Persona 反事实证据必须对同一冻结 source/research dossier 独立执行 with-persona 与 without-persona 两次 current-task 判断，并分别保存输入、输出、provenance 和 hash；禁止通过把人工 control 字段合并回 with-persona output 来构造“事实稳定/只改变表达”的证明。
- run 存在 source/research 候选失败时，整体状态必须显式 non-ok/partial，整体 `quality_gate_ok` 不得保持绿色；如需表达存活候选质量，只能使用明确命名的 `survivor_quality_gate_ok`，不能让部分成功被读成整批通过。没有 opened external research result 的候选必须 typed research failure 并排除出 Stage 1，不能先标 eligible 再依赖后置 recommendation guard。
- 候选级失败必须记为明确失败并排除出推荐；同批其它证据完整候选可以继续，但 run 必须标为 `completed_with_failures` 或等价非成功状态，不能把部分成功汇报为整批成功。
- 旧实现的恢复能力只通过 Git commit、release artifact 和明确回滚版本提供；不得在 active runtime 中复制一套旧逻辑作为隐形备用路径。
- deterministic 数据仅可用于无内容结论的单元测试 fixture；不能成为可选 engine、开发自验内容证据、QA 通过证据或生产降级路径。

## 发布前全量回归

- 全量回归不是单需求 QA，也不是在未合并生产基线的 dev 分支上多跑一遍测试。
- 发布前必须先形成 release candidate：把当前生产代码和本次待发布需求代码合成到同一个候选状态中，再做全量业务回归。
- 全量业务回归的目标是证明“发布后真实生产不会出问题”，因此必须覆盖跨需求组合后的主业务链路、外部写入、卡片/SCF 回调、06 生成与写表、Skill 输出、旧数据迁移/回填、失败守卫和生产只读反查。
- 全量回归必须在生产正式更新前完成；生产更新后只做最小 production smoke，不用 smoke 代替全量回归。
- 如果 release candidate 回归失败，不能继续发布；必须先定位是代码、配置、数据迁移、测试资源还是发布包差异问题，修复后重新形成候选状态再回归。
- 发布前必须列出真实运行环境清单，并逐项确认发布路径和验证方式。AI 账号雷达至少包括：production repo、runtime copy、LaunchAgent/watcher、global private Skill、production SCF receiver、Feishu production schema/views/backfill、ledger/telemetry、Topic Card sender/receiver。只更新 repo 不等于真实环境已发布。
- 发布前必须做部署通道 preflight：确认 SCF、runtime、Skill、schema/backfill 等每个生产动作由什么命令或控制台路径执行、如何验证 hash/版本/health、失败时在哪里停止。部署通道不可用时不得进入后续生产写入。
- PM 发布汇报必须区分：单需求 QA 结论、release candidate 全量回归结论、production smoke 结论。三者不能互相替代。
- RC 全量回归通过后，PM 线程只能进入发布授权决策和派发，不得自行执行生产发布。发布执行必须由生产线程按任务卡完成，并把每一步的命令、输出、写入范围、失败/回滚证据回传 PM。
- 如果 PM 线程误执行了生产动作，必须立刻停止后续发布，先做影响盘点、防复发修复和用户汇报；不得用“已经开始了”作为继续发布的理由。
- 发布后最小 production smoke 可以由生产执行线程完成，用于确认部署、runtime、SCF、Skill、字段/视图、权限和关键守卫在真实环境生效；但它只能验证“发布没有明显断裂”，不能替代测试线程的业务回归。
- production smoke 命令必须显式只读或明确受控。凡是命令名/参数存在歧义，例如 `--no-notify` 这类只禁止通知但仍可能写数据或发送卡片的入口，不得当作 dry-run 或只读检查。需要只读检查时必须使用 `--check-only` 或等价保证：不写飞书业务表、不发卡、不写 ledger、不写 decision card、不触发采集、不触发真实 06/Codex。
- 发布后如需要业务回归，应由测试线程执行，且必须设计成不产生或最小化生产数据影响：优先只读、staging/test、已有受控生产记录、dry-run 或明确可清理的测试标记；不得为了回归而随意发真实卡、触发真实采集或生成真实 06。
- 发布结果汇报必须逐需求说明：本轮最终发布了哪些 AR、每个 AR 给用户带来什么变化、发布时做了哪些生产动作、哪些 smoke/回归证据证明它生效、哪些风险或后续任务尚未关闭。不能只说“发布完成”。

## 生产恢复规则

- 生产恢复的默认目标是“业务链路在当天/目标批次的合理完整恢复”，不是“最小样例恢复”。除非用户明确说“只做最小恢复 / 只做 smoke / 只验证一条样例”，PM 和生产线程不得把少量样例成功当作恢复完成。
- 恢复前必须先定义恢复口径：目标日期/批次、应覆盖的数据源或账号池、生产默认覆盖量、可接受的降级范围、停止条件、失败后如何可见和可恢复。
- 恢复过程如果临时降级，例如限制账号数、降低 retry、跳过某类数据源、只跑部分链路，必须显式标记为 `partial recovery` 或 `limited recovery`，并说明为什么降级、覆盖了多少、没覆盖什么、是否需要继续恢复。不能在摘要里把低覆盖恢复说成完整恢复。
- 恢复完成必须提供覆盖证据，而不只是链路 `ok=true`：例如计划账号数、实际尝试账号数、成功账号数、失败账号和原因、数据条数、来源分布、read-back、latest/logs/控制台是否一致。
- 如果用户要求“恢复生产数据”，默认应恢复到项目正常生产口径；AI 账号雷达里，采集恢复至少要对齐生产默认采样覆盖，而不是任意较小的人工参数。
- PM 验收生产恢复时必须检查恢复口径是否满足用户目标。若实际只是最小恢复、样例恢复或限流恢复，应标为 `Partial Recovered / Needs Full Recovery`，不能 PM Accepted。
- 若完整恢复存在真实风险，例如平台风控、登录验证、长时间运行、重复写入或外部服务限制，必须把风险和替代口径交给用户决策；不能自行把恢复目标降到最小。

## 用户可见输出 QA

- 涉及飞书卡片、飞书文档、06 口播包、学习确认卡、通知、状态字段、SCF 回写和定时任务产物时，测试必须提供真实样例证据。
- 测试结论必须包含真实输入、真实输出路径或链接、关键输出片段、人工确认点和环境边界。
- 只有代码测试通过但没有真实样例证据时，不能标为最终 Ready，只能标为 `QA Passed / Waiting User Review` 或等价状态。
- 真实测试不等于写生产；优先使用 staging/test、隔离测试表、测试文件夹、个人测试通知目标、本地 dry-run 输出或生产只读样例。
- 飞书测试卡属于正常 QA 流程，后续不需要每次向用户单独申请授权；但必须走 staging/test 表、测试应用或个人测试接收目标，并明确标记为测试卡。测试卡不得写生产业务表、不得发到正式业务目标、不得触发真实生产采集、不得触发真实 06 生成路径。测试资源、OAuth 或测试接收目标不可用时，应标为阻塞并回传 PM，不能降级使用生产路径。
- 未经用户明确授权，不得写生产业务表、发真实业务卡片或触发真实生产采集。
- 用户可见点测不是完整测试。测试计划必须覆盖需求所在链路的上游输入、核心处理、外部写入、用户可见输出、旧数据迁移/回填、失败/回滚路径。只验证按钮、链接或字段表面行为，不能把整条需求标为 QA Passed。
- 新增代码测试不是完整测试。测试线程不能只围绕新增函数、mock 或 fixture 验证新增逻辑；必须补“流程测试”和“回归测试”：流程测试覆盖真实入口到用户可见产物的主链路，回归测试覆盖该需求可能影响的既有链路、相邻状态流转、历史数据、异常/恢复路径和发布守卫。
- 若本轮只完成新增代码/控制流测试，应标为 `Control QA Passed / Needs Flow + Regression QA` 或等价状态，不能标为完整 `QA Passed`。只有主流程、关键回归、用户可见结果和失败边界均被验证后，才可进入发布候选。
- 对 06 链路类需求，至少要分开验证：06 生成/同步产物如何形成、06 记录如何写入飞书、字段/视图如何展示、学习/反馈读回是否兼容、旧记录如何 backfill、新记录发布后如何 smoke。

## 测试等级与通过口径

- `L0 静态审计`：读代码、读 diff、读文档、检查提交范围。只能发现明显风险，不能单独称为 QA 通过。
- `L1 单元/函数测试`：mock、stub、本地函数探针、py_compile、diff check。只能证明控制流和格式规则，不证明真实外部系统体验。
- `L2 API 集成测试`：在 staging/test 表、测试文件夹、个人通知目标中真实写入或只读 read-back，证明外部 API 接受 payload、字段类型正确、数据可读回。
- `L3 用户可见交互测试`：打开真实测试表/测试文档/测试卡片/测试通知，从用户界面验证可见性、可点击、状态展示、按钮/链接跳转、错误提示和视图位置。涉及“能点击”“能看到”“能操作”的需求，至少要到 L3。
- `L4 生产最小 smoke`：发布后在生产真实运行环境做最小范围读回或一条受控真实链路验证，确认发布环境配置、字段、视图、权限和 runtime copy 生效。
- `Flow 流程测试`：从真实或等价入口开始，串起上游数据、核心处理、外部写入、用户可见产物、回调/后续动作，验证链路整体能闭环。飞书卡片类需求至少要覆盖 build/preview、发送或测试发送、用户操作回调、状态写回和后续卡片/任务触发。
- `Regression 回归测试`：验证本需求影响范围内既有主流程不退化。至少覆盖原有当天发卡、无历史候选发卡、已处理候选排除、unknown guard、dev 发卡守卫、回调幂等/过期/重复提交等相邻路径。
- 测试报告必须写明本轮达到的最高等级。不能把 L0/L1/L2 说成 L3/L4。
- 对用户可见体验类需求，API read-back 只能作为前置证据；如果没有 UI/交互验证，只能标 `QA Incomplete / Needs Real Test` 或 `Waiting User-visible QA`。
- 对飞书字段类需求，真实测试数据必须至少包含：测试表字段 schema、测试记录 record_id、写入 payload、read-back payload、用户界面可见性/点击证据；如果无法自动点击，需要测试线程给出截图、浏览器验证记录或明确阻塞原因。
- 多页卡片截图必须逐页校验页身份：截图内容中的候选数、首条 candidate/title、run marker 与对应 page manifest/DOM 必须一致。仅有正确文件名或完整 DOM 不能证明截图属于该页；错页、重复页或从中段开始的“page top”一律视为可见证据未闭环。

## 浏览器测试边界

- 浏览器/UI 测试默认不得打断用户当前浏览器工作。
- 优先使用后台/隔离浏览器、应用内浏览器、独立 Chrome profile、临时 profile 或可关闭的测试窗口；不要默认复用用户正在工作的前台 Chrome 标签。
- AI 账号雷达飞书 L3 测试优先复用独立 Chrome profile：`ai_account_radar_dev/.runtime/browser-profiles/feishu-l3-test`，调试端口 `9227`。该 profile 只用于 staging/test 飞书 UI 验证，不保存到 Git，不写生产。
- 如果必须使用用户已有登录态或前台 Chrome，测试线程必须先说明原因并等 PM/用户授权；授权后尽量只短时间置前，完成后关闭测试 tab 或恢复原窗口。
- 如果 UI 测试因为登录态、二次验证、权限或浏览器授权无法在后台完成，应标为 `UI Test Blocked / Needs User Auth`，不能降级成 API read-back 通过。
- 测试报告必须说明浏览器测试是否影响了用户前台工作，以及使用了哪个浏览器/profile/session。

## 内容生成 QA

- 内容类生成测试必须验证体感质量，而不只是结构命中或单测通过。
- 当用户用具体样例说明内容问题时，PM 和开发必须抽象成 Skill 方法优化，而不是只修当前两条样例；样例应作为回归用例和验收证据。
- Skill 方法优化不能写成固定段落、固定句式、固定顺序或必须逐条出现的口播规则；应写成生成前的判断框架、素材组织方式和可变表达原则，避免再次造成同构和模板化。
- 必须检查是否更像用户、是否避免 AI 味和模板化、是否有当前选题搜索或同类来源、是否有表达模式拆解、是否融合成用户账号风格。
- 对标学习不能写成无证据结论；无法实时搜索时，必须说明，并使用已沉淀对标素材或向 PM / 用户要来源。
- 概念类名词必须用普通人听得懂的案例、比方或具体业务场景解释，不能写成百科定义或工具教程。
- 测试线程不能只给分数，必须给用户能阅读的样例、关键片段和不通过理由。

## Skill 测试门禁

- 仓库脱敏 Skill 只用于 Git、迁移、同步和显式回归。
- 涉及 `austin-no-overtime-scripting`、`austin-voice-scriptwriter` 或其他生产私有 Skill 的内容质量变更，脱敏仓库镜像 / deterministic fallback 测试只能算前置。
- 测试阶段不得直接修改生产全局 Skill。
- 测试阶段应建立测试环境私有 Skill 副本，并让 runner / `codex exec` 明确调用测试 Skill。
- 测试通过和用户确认后，发布阶段才允许同步生产全局 Skill，并做最小 production smoke。
- 若测试 Skill / `codex exec` 因审查、超时、凭证或路径问题无法运行，应记录为阻塞或发布风险，不能退回脱敏版假装通过。
- 对已确认零 fallback 的 Skill 重构，repo mirror 是唯一 Git 管理的发布源，测试副本与 global private Skill 必须由它生成并做 hash read-back；旧 Skill 内容必须从 active contract 删除，不能以“兼容模式”“备用 Skill”或环境变量开关继续存在。
