# 飞书选题卡片云端接收可行性验证

日期：2026-06-21

## 结论

交互式选题卡片的点击回写逻辑可以从本机 receiver 迁到云端，但不能简单依赖「多维表格自带自动化」完成。

原因是当前需求的触发源不是表格字段变化，而是消息卡片里的 `card.action.trigger` 表单提交。这个事件需要一个应用后端接收、解析 `form_value`，再调用多维表格 API 更新 `04 分析与选题` 的多条记录。

## 本次验证结果

已验证当前代码具备迁移到云端 receiver 的必要结构：

- 支持飞书事件订阅 URL 校验：收到 `challenge` 后返回 `challenge`。
- 支持校验飞书回调 token。
- 支持解析卡片事件中的 `event.action.value` 与 `event.action.form_value`。
- 支持把用户选择映射成多条 04 记录更新。
- 支持重复提交保护，避免同一张卡片重复点击造成重复写入。

本地模拟结果：

- `challenge` 模拟请求返回成功。
- 卡片提交事件模拟请求能返回飞书卡片需要的 toast 响应结构。

## 平台可行性判断

### 不推荐：多维表格自带自动化

多维表格自动化适合「记录新增 / 字段变化 / 条件满足」后触发发送消息、更新字段等动作。但它不是卡片事件接收器，不能自然承接用户在消息卡片里一次勾选多条记录后的 `form_value`。

### 条件可行：飞书集成平台 / 飞书自动化平台

只有在同时满足以下条件时可行：

1. 能对外暴露一个 HTTP/Webhook 接收地址，作为飞书开放平台事件订阅回调地址。
2. 收到 URL 校验事件时，能按原请求动态返回 `{"challenge":"..."}`。
3. 收到卡片提交事件时，能解析 JSON 里的 `event.action.form_value`。
4. 能发起 HTTP 请求调用飞书多维表格 API，更新指定 record_id。
5. 能保存或查询提交指纹，做重复提交保护。

如果飞书集成平台只能接收普通 webhook，但不能自定义即时响应 body，尤其不能动态返回 `challenge`，则不能直接作为卡片事件 receiver。

### 稳定可行：云函数 / 轻量云服务

把当前 `serve-callback` 逻辑迁成云函数或轻量 Web 服务是最稳的方案。它不依赖本机在线，也不受自动化平台能力限制。

## 推荐方案

短期验证：

1. 保留现有交互卡片发送逻辑。
2. 把 `serve-callback` 的核心处理逻辑拆成云函数 handler。
3. 在飞书开放平台把事件订阅方式从长连接改成 HTTP 回调。
4. 订阅 `card.action.trigger`。
5. 用一张测试卡片验证外部用户提交后能写回 04。

中期生产：

- 每日定时发送卡片可以继续由本地脚本、服务器 cron 或飞书自动化触发。
- 卡片点击回写由云端 receiver 承接。
- 04 写回后再触发选择学习和 05 生成。

## 当前判断

飞书自动化平台不是完全不能用，但它必须扮演「云端 HTTP receiver + API 调用器」的角色，而不是普通多维表格自动化。

如果平台无法满足 `challenge` 动态响应和卡片事件 JSON 解析，建议直接使用云函数。

## 2026-06-21 路线更新

已决定优先走云函数 receiver 路线，不再把本机长连接 receiver 作为生产方案。

已新增可部署包：

```text
cloud_functions/feishu-card-receiver/
```

当前版本采用 Node/Web Fetch API 形态，核心文件为：

```text
cloud_functions/feishu-card-receiver/src/receiver.js
```

它已经覆盖：

- 飞书 `challenge` 校验；
- `card.action.trigger` 表单提交解析；
- 04 多条记录回写；
- 重复提交 no-op；
- 本地单元测试。

后续只需要选择云函数平台，把环境变量配置进去，再把云函数 HTTPS 地址填入飞书开放平台事件订阅。
